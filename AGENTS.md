# AGENTS.md

Guidance for AI agents (and humans) working in this repository. This project is **EFTForge** - a full-stack Escape from Tarkov weapon build simulator and community build-sharing platform.

For feature-level documentation see [README.md](README.md) (English) / [README_ZH.md](README_ZH.md) (Chinese). For local dev setup, lint/test commands, and code style rules, see [CONTRIBUTING.md](CONTRIBUTING.md). This file complements those - it captures architecture context and working-agreement rules an agent needs before touching code.

---

## Repo layout

| Path | What it is |
|---|---|
| `backend/` | Python/FastAPI server. All item data, build calculation, the MILP optimizer, ratings, community builds, profiles, admin tools. SQLite via SQLAlchemy. |
| `frontend/` | Vanilla JavaScript (ES2022) SPA. Classic `<script>` tags sharing a global scope, **not** ES modules - cross-file functions are declared as ESLint globals, not imported/exported. |
| `desktop/` | Windows desktop app: Tauri 2 shell (Rust) wrapping a WebView2 window pointed at a PyInstaller-frozen copy of the backend running as a local sidecar exe. See [desktop/README.md](desktop/README.md). |
| `template/` | Seed/template JSON (e.g. `announcements.json`) used when provisioning a fresh environment. |
| `local-app/` | Empty except `node_modules/` - not tracked in git, not part of the shipped project. Leftover/scratch; don't treat it as a real module. |
| `readme-assets/` | Images/SVGs referenced by the READMEs. |
| `launch.bat` | One-shot local dev launcher: builds/syncs the DB on first run, starts the FastAPI backend on `127.0.0.1:8000`, serves the frontend on `127.0.0.1:5500`, opens the browser. |

## Backend architecture (`backend/`)

- **Entry point:** `main.py` - app wiring only: middleware, database creation, startup tasks, and mounting the routers. Add new endpoints to a router, not here.
- **Routes (`routers/`):** one `APIRouter` module per feature: `system` (health, sync status, data version), `proxy`, `catalog` (traders, ammo, items, slots), `guns`, `build_calc`, `combo`, `optimizer`, `images`, `ratings`, `leaderboard`, `stat_changelog` (the Stat Tracker's history), `armor` (read only, for the Ballistics Workbench's engine in the browser: the armor catalog, `/armor/zones`, `/armor/constants` from `spt_armor_stats.json`, and `GET /armor/chart`, the precomputed ammo effectiveness chart; no armor simulation runs on the server), `profile`, `community_builds`, `comments`, `admin_builds`, `moderation` (bans, authors), `announcements`, `atlas` (serves the game data change sets in `ATLAS_EXPORT_DIR` (PvP Season's), and Arena's, PvP's and PvE's in `ATLAS_ARENA_EXPORT_DIR`, `ATLAS_PVP_EXPORT_DIR` and `ATLAS_PVE_EXPORT_DIR` under `/atlas/api/arena`, `/atlas/api/pvp` and `/atlas/api/pve`, time-gated for the public, with personal access keys (each key has scopes: `changes` opens the change sets, `lookup` gives the player lookup its own allowance, and `early`, given only on purpose to trusted sites, lets the feed serve sets before they're public; a new key without named scopes, and a key made before scopes, has `changes` and `lookup`); the key-only, never-cached feed other sites' servers pull them from under `/atlas/api/v1/{game}/` (`changes` with a cursor, `sets`, `values`), which stops working for a key the moment it is revoked and holds sets back until they're public unless the key is `early`; the per-datacenter matching times in `ATLAS_MATCHING_DIR` under `/atlas/api/matching`, live and ungated; plus the admin switch that shows or hides the header's Atlas button, hidden by default), `atlas_lookup` (`GET /atlas/api/lookup/search?nickname=` and `GET /atlas/api/lookup?accountId=`, plus `GET /atlas/api/lookup/banned?accountId=`, the ban guess as tarkov.dev makes it (`ban_guess`: the profile's current nickname searched in the same mode; `possibly_banned` when the search leaves the account out, `no_sign_of_ban`, or `unknown` for a name the game won't search), served so other sites don't each redo it wrong; `/atlas/api/lookup/search` answers a name Atlas' own player index knows from it (`services/player_index.py`, `source: "index"`, no game request and no allowance used; `live=1` forces the game's search, which the players page does when the profile it opened from the index has another name); `art=0` on `/atlas/api/lookup` leaves out every Kitbash! drawing for other sites' stats syncs, kept in the minute's cache apart from the page's; open to everyone, forwards to Atlas' upstream provider at `ATLAS_LOOKUP_URL`, adds tarkov.db art, Kitbash! drawings of each weapon and helmet, each weapon's builder payload with every part's slot id, and each piece of gear's worn armor class, the player's character drawn by Kitbash! (`character`: a headshot and a full body from the profile's `customization` suits and worn gear, the full body also holding the player's gun in its right hand (the primary, else the secondary, else the pistol, in a pose for its type), which the loadout board shows behind its slots in place of the stock PMC; with Kitbash!'s 3D render service at `KITBASH_RENDER_URL` it also has `full3d`, the full body in 3D with every carried weapon where the game puts it, served from `GET /atlas/api/lookup-render/<spec>/<weapon slot or none>/<pose>` (or straight from an account, `GET /atlas/api/lookup-render?accountId=&mode=&hand=&pose=`, which looks the profile up as `/atlas/api/lookup` does and redirects there, uncached): the spec is kept on disk in `RUNTIME_DIR/lookup_specs` by its hash, a picture is drawn on first request (only those count against the IP's render allowance in `lookup_guard`) and kept with the drawings, and the board's weapon and pose dropdowns, shown while the slots are hidden, switch between them; the headshot shows the face's name on hover from the provider's `clothing.head`), plus the same art, drawings and builder payloads for the favorite items, and each weapon mastering's weapon icon and names; what's inside a player's containers is never shown, since the game only shares it with friends of the account lookups come from; unset, as in production for now, it answers 503; `services/lookup_guard.py` rate limits each IP in a SQLite file every worker shares (or each Atlas key, for another site's server sending one the way the v1 feed takes it; a key may only hold a few of the in-flight slots, and all keys together only send `KEY_SHARE` lookups per mode per 10 minutes on to the provider, `KEY_SHARES` for PvE, so the players page keeps most of each mode's budget), caps lookups in flight server wide (`ATLAS_LOOKUP_MAX_IN_FLIGHT`) and caches answers for a minute (ten for a key), keeping them six hours so a mode that can't be looked up right now (the provider busy or the game refusing) still answers with the last one it had, marked `stale`; a name the game won't search (it filters the text itself, err 226, even for a name a real account holds) is remembered per mode for a day and answered `unsearchable_name` without asking again, after the player index has had its turn; identical lookups in flight share one request; and only known error codes reach the browser; each Kitbash! drawing goes out as its own address, `GET /atlas/api/lookup-art/<hash>`, kept on disk in `RUNTIME_DIR/lookup_art` (oldest pruned past 200 MB) and cached for a year, outside `/atlas/api/lookup` so nginx's flood limit there doesn't count pictures. There's deliberately no total lookup cap for the server). `routers/shared.py` holds the DB session dependencies, client IP/ID hashing, `require_admin`, request validation limits and the item/user text helpers. `main.py` includes the routers in a fixed order, so keep any route that could match the same path as another one in the right order. A new top-level path still has to be added to the prod nginx allowlist.
- **Services (`services/`):** logic with no routes of its own, shared by routers: `sync` (hyperactive sync and the catalog data version), `solver_cache`, `solve_limits` (solver rate and concurrency guards), `gitee` (card image and avatar storage), `build_cards` (card drawing and the migration worker), `conflicts`, `player_index` (a `player_index` (Atlas' own player index, account ID to current nickname per mode, in `RUNTIME_DIR/player_index.sqlite3`: every profile Atlas looks up and every player a live search lists is recorded, and recording a name drops any other account still under it, so renames sort themselves out; each name an account loses that way (renamed itself, or its name now held by another account) is kept as one of its past names (`past_names`, newest first, at most 20, a case change not counted, a name it takes back no longer past), which `/atlas/api/lookup` answers with as `pastNames`; each mode is seeded once from tarkov.dev's `players.tarkov.dev/<mode>/index.json`, fetched with Atlas' own User-Agent and read as a stream, PvP keeping only accounts refreshed there within 180 days (about 113k of 3 million); seeding never overrides a name Atlas has seen, `reseed(mode)` imports again by hand, and it only runs while `ATLAS_LOOKUP_URL` is set; key holders get it through `GET /atlas/api/players/{mode}/index.json` (account ID to nickname) and `updated.json` (account ID to when Atlas last saw it, Unix ms, only for accounts Atlas has seen itself), tarkov.dev's own shape, for keys with the `lookup` scope only, never cached, each file rebuilt at most hourly into `RUNTIME_DIR/player_index_export`y` (forwards community endpoints to the live site for the desktop app's connected mode and the DEV modal's local dev connected mode). Runtime flags that get rebound (`services.sync.sync_running` and friends) are read as module attributes, never imported by value.
- **Schema upgrades:** `db_migrations.py::prepare_databases()` runs once at startup under a cross-worker file lock. `builds.db`, `ratings.db` and `changelog.db` are versioned: each keeps its version in `PRAGMA user_version`, and every newer function in its `*_MIGRATIONS` list runs in one transaction together with its version bump. A brand-new database is created from the models and stamped current without running migrations. To change one of those schemas, append a migration (use `add_column()` so it stays a no-op where `create_all` already made the column) and never edit, remove or reorder one that has shipped. `tarkov.db` is not versioned: new model columns and indexes are added to it automatically, because its rows are regenerated by every sync.
- **Desktop entry point:** `desktop_main.py` / `desktop.py` - same backend, run in "desktop mode" (`EFTFORGE_DESKTOP=1`), serving the frontend as static files and gating admin/local-only endpoints to `127.0.0.1`.
- **Databases:** four separate SQLite DBs, each with its own engine/session and model files:
  - `tarkov.db` via `database.py` - item/slot/trader data synced from tarkov.dev (`models_items.py`, `models_slots.py`, `models_slot_allowed.py`, `models_traders.py`, `models_item_offers.py`, `models_weapon_presets.py`, `models_armor.py` for armor pieces and plate slots).
  - `ratings.db` via `database_ratings.py` (`models_ratings.py`) - attachment/build voting.
  - `builds.db` via `database_builds.py` (`models_builds.py`) - published community builds, comments, notifications, bans, announcements.
  - `changelog.db` via `database_changelog.py` (`models_stat_changelog.py`) - the Stat Tracker's history: every sync diffs the tracked weapon, attachment and ammo stats against `stat_snapshot.json` (written by the previous sync) and logs the changes and new items.
- **Optimizer (`backend/optimizer/`):** constraint-based MILP solver (HiGHS backend) that fills every attachment slot at once.
  - `solver.py` - main `optimize_weapon` / `OptimizeParams` entry point, stat ranges, MOA floor.
  - `milp.py` - the actual MILP formulation.
  - `compat_map.py` - builds the slot/item compatibility map the solver searches over.
  - `feasibility.py` - pre-solve feasibility checks.
  - `pricing.py` - trader/flea pricing logic feeding the solver's budget constraint.
  - `explore.py` / `explore_request.py` - bounded tradeoff sampling for the current weapon, request validation, and filtering of duplicate/dominated results. `POST /build/explore` shares the optimizer's rate and concurrency guards. Each curve shares one solver deadline and retains usable partial results. **Explore mode is the optimizer's default and only mode** - single-solve mode is scrapped/permanently disabled, so "the optimizer" means Explore mode unless stated otherwise.
  - `gunsmith.py` - **backend-only, not exposed in the frontend UI** (see Gunsmith mode note below).
- **Sync:** `sync_tarkov_dev.py` pulls item/slot/trader data from the tarkov.dev static JSON API (`json.tarkov.dev`), including language overlays. It's invoked automatically by `reset.py`, which `launch.bat` calls. Do not run `sync_tarkov_dev.py` directly during local dev - it's for manual out-of-cycle resyncs on the live production server only.
- **Stats:** `stats.py` holds the shared backend build-stat calculations (`_calc_aiming_stats` is the canonical TrueErgoDelta/overswing/arm-stamina/aim-sway formula set, matching the game's own rules; `MOA_K`, `overswing_limit_kg`/`overswing_limit_slope` and `ted_cost_per_kg` are imported by `optimizer/milp.py` rather than re-typed). TrueErgoDelta (TED) is the build's effective ergo (up to 100) minus the ergo its weight needs, 100 x (1 - 3 / weight) above 3 kg: how much ergo it could lose before aiming in overswings. TrueErgo is the optimizer mode that maximizes it. These formulas are **intentionally duplicated** in `frontend/modules/calculations.js` for real-time client-side calculation - keep those copies in sync by hand, there is no codegen between Python and JavaScript. `backend/tests/data/stat_formula_golden.json` holds shared input/output vectors that `backend/tests/test_calculations.py` and `frontend/tests/calculations.test.js` both check their respective copy against, so an unsynced edit fails a test on whichever side changed instead of silently drifting.
- **Ballistics:** `ballistics.py` is the armor engine: kill chance and armor wear shot by shot for one ammo against the armor layers covering one spot, following the game's own rules. It tracks exact state probabilities rather than sampling random shots, reads its armor constants from `spt_armor_stats.json`, and `backend/tests/data/ballistics_golden.json` holds reference curves it's checked against. `spt_armor_stats.json` also carries the player model's colliders (which body part each one drains, and the values plate colliders pass on), which `extract_spt_stats.py` keeps as they are. It also flies the bullet with G1 drag in 0.01 s steps, so a distance turns into the arrival speed that weakens damage and pen. It covers buckshot (every pellet in turn), ricochets at an angle, and hits to the stomach or limbs, whose damage past 0 spreads until the thorax or head goes (`spread_capacity`). Runs take a `deadline` so a slow setup returns the shots it finished instead of hanging. **`frontend/modules/ballistics-engine.js` is a by-hand port of it** that the Ballistics Workbench runs in a Web Worker on the player's own machine, on the website and in the desktop app. The requests the workbench makes (armor simulation with its layer building and loadout rules, caliber comparison, drop table) live only in that file, never on the server; `frontend/tests/ballistics-requests.test.js` covers them. On the backend, `ballistics.py` only feeds `ammo_chart.py` and the golden tests. Keep the two engines in step: `backend/tests/test_ballistics_engine_golden.py` checks `backend/tests/data/ballistics_engine_golden.json` still matches `ballistics.py` (rewrite it by running that file), and `frontend/tests/ballistics-engine.test.js` checks the port against it. `ammo_chart.py` precomputes the ammo effectiveness chart (every round against every armor setup, deduplicated) into `RUNTIME_DIR/ammo_chart.json`, with a checked-in `ammo_chart.json` as the starting copy. Each cell is keyed by hashes of its own inputs, so the refresh started after every sync only works out cells whose ammo, armor or constants changed; bump `ENGINE_VERSION` whenever the engine's results change. Production never runs that refresh (`AMMO_CHART_REFRESH=0` in its `.env`): the maintainer computes the chart on their own machine and ships the checked-in `ammo_chart.json`, which prod serves as is.
- **Config:** `config.py` reads `.env`. `IP_HASH_SECRET` and `ADMIN_API_KEY` are required (server refuses to start without them); everything else has defaults. `config.py::_resolve_desktop_data_dir()` must stay in sync with `desktop/src-tauri/src/main.rs::resolve_data_dir()`.
- **Tests:** `backend/tests/` - pytest, covering the optimizer/solver (termination, sparse constraints, ammo handling, concurrency, API regressions), gunsmith, combo transport, reachability, and the TrueErgoDelta/aiming calculation formulas.

## Frontend architecture (`frontend/`)

- **No build step, no bundler.** `index.html` loads `app.js` and each `modules/*.js` file via plain `<script src="modules/x.js?v=HASH">` tags, in dependency order. Every module attaches to a shared global namespace rather than using `import`/`export`.
- **`app.js`** - core app bootstrap, shared UI setup, and update/sync notices. Client-side TrueErgoDelta, aim-sway and arm-stamina helpers live in `modules/calculations.js` (kept in sync with `backend/stats.py` by hand).
- **`modules/`** - one file per feature area: `api.js` (backend calls), `state.js`, `tree.js` / `attachment-grid.js` (the two workbench views), `slot-selector.js`, `optimizer.js`, `graph.js` (attachment graph), `calculations.js`, `build-manager.js` (saved builds and loading), `build-codes.js` (share code encode/decode), `build-publish.js`, `community-builds.js`, `notifications.js`, `tab-manager.js` (workbench tabs and session management), `build-preview.js`, `builder-3d.js` / `builder-3d-panels.js` (the opt-in 3D builder, 2D until the user picks 3D: the Kitbash! viewer in an iframe at `config.VIEWER_URL`, driven only over its postMessage protocol, with our own panels on top; no Kitbash! code lives in this repo), `ammo-table.js`, `ballistics-workbench.js` (the Ballistics Workbench: the header's Ballistics button opens it as its own build tab, `kind: "ballistics"` in `tab-manager.js`, or as a page on mobile; it swaps the builder's left and right panel content via `.ballistics-mode` and pops item pickers out on the right like the attachment table), `armor-sim.js` (its armor simulator: a TarkTetris-style loadout panel whose item table doubles as the armor data sheet, with default plates, conflict checks and Kitbash! helmet icons), `ballistics-tools.js` (its effectiveness chart and drop table), `leaderboard.js`, `profile.js`, `tracker.js` (Stat Tracker: the quick overview of new items and stat changes from our tarkov.dev syncs, with a note that links to Atlas once the Atlas button is switched on), `news.js`, `lang.js` (i18n), `desktop-settings.js`, `window-controls.js` (desktop titlebar), plus `*-devtool.js` files for localhost-only dev panels. `atlas.js` is the exception: it belongs to Atlas, a standalone project (never describe it as part of EFTForge or as a sister project; it is only hosted on eftforge.com for cost and ease of development) served at `/atlas` and, for Arena, `/atlas/arena` (`atlas/index.html`, with `atlas/arena/index.html`, `atlas/pvp/index.html` and `atlas/pve/index.html` identical copies since the path picks the game; each page loads its own mode's change sets, `css/atlas.css`, its own logo and wordmark in `assets/images/atlas-*.svg`), reached from the header's Atlas button (the desktop app opens the live page in the browser). `atlas.js` also runs the change tracker's first-visit tour and the quick start guide behind its Guide button; both are inserted before `#eft-tooltip`, because the watermark guard needs the watermark to stay the last element in `<body>`. Every Atlas page's header has the game mode switch in the middle (PvE, PvP, PvP S, Arena; `modules/atlas-mode.js`, remembered across pages; a mode lights up on a page once that page has something for it) and the Changes (the remembered mode's change tracker), Servers and Players buttons before the wordmark. - **`?v=HASH` cache-busting params** in `index.html`: these are content hashes, not hand-picked numbers - **never edit them yourself** (see Working Agreements below). `scripts/release_prep.py` regenerates them (and stamps `APP_BUILD_DATE` in `modules/config.js`) from the actual file bytes; the maintainer runs it right before a prod release.
- **Tests:** `frontend/tests/` - minimal, currently `combo-api.test.js`, `combo-view.test.js`, `explore-api.test.js`, `atlas.test.js`, `calculations.test.js` (the golden-vector check against `backend/stats.py`, see Stats above), `ballistics-engine.test.js` (the same for `backend/ballistics.py`, see Ballistics above), and `ballistics-requests.test.js` (the workbench's requests to that engine). No broad frontend test suite exists yet.
- **Linting:** ESLint per `.eslintrc.json` (`npm run lint` from `frontend/`).
- **Type checking:** `npm run typecheck` (TypeScript over `jsconfig.json`, no build step, runs in CI) checks every script (`app.js`, `modules/`, `data/`); a new module is checked by default. Types come from JSDoc (`/** @type {HTMLInputElement | null} */ (document.getElementById(...))` and friends), so the shipped JS is unchanged. Names reached through `window.` or `EFTForge.`, and custom properties stored on DOM elements, are declared in `frontend/types/globals.d.ts`; add new ones there.

## Desktop app (`desktop/`)

Tauri 2 (Rust, `src-tauri/`) + a PyInstaller-frozen backend sidecar (`pyinstaller/`). The frontend is the same codebase served locally instead of over the internet. Key points if working in this area:
- Data dir resolution is portable-first (`<install dir>/data/`), falling back to `%LOCALAPPDATA%` only if the install dir isn't writable - logic duplicated in Python and Rust, see above.
- Local server port defaults to 47651, then tries 47652 through 47660, with an ephemeral port as the final fallback. Preserve the preferred port because localStorage is origin-scoped. `EFTFORGE_PORT` can explicitly override it.
- Desktop mode is dev mode: `window.__EFTFORGE_DESKTOP__`, a local admin key auto-generated to `data/admin.key`, every localhost-gated devtool active.
- Release flow: bump version in `src-tauri/tauri.conf.json` + `Cargo.toml`, tag `app-vX.Y.Z`, push - `.github/workflows/desktop-release.yml` builds and publishes.

## CI

`.github/workflows/ci.yml` runs on pushes/PRs matching its path filters (backend, frontend, and selected lint/CI configuration files): `black --check`, `flake8`, `pytest` for the backend, plus `eslint` and frontend regression tests (`npm test`) for the frontend. `mypy` runs but is currently non-blocking. These describe CI checks; the working agreement below still governs local frontend verification. Backend formatting is `black` at line length 120 (`pyproject.toml`); `.flake8` documents the handful of deliberately-ignored rules (E501, W503, E221/E272 for aligned dict columns, E402 for `sync_tarkov_dev.py`'s dotenv ordering, E712 for SQLAlchemy's `== True` DSL).

## Working agreements

These apply specifically to this repository and override generic default behavior:

1. **The AI agent should never launch or check the frontend.** No dev server, no browser, no Playwright/screenshotting against `frontend/`. The maintainer verifies all frontend/UI changes manually. Backend-only verification (Python scripts, pytest, syntax checks) is fine.
2. **Never manually-edit the `?v=HASH` cache-busting params** on `<script>` tags in `frontend/index.html` when editing a `frontend/modules/*.js` file. The tags are regenerated by `scripts/release_prep.py`, which the maintainer runs right before a prod release.
3. **"Write a commit message" means output text only.** Never run `git add`/`git commit` (or any git command) on that request alone - only act on an explicit "commit this" / "make the commit".
4. **Commit messages / patch notes / changelogs:** only describe a fix as a "bug fix" if the bug existed in a version that actually shipped to users. Bugs introduced and fixed within the same unreleased feature work fold silently into the feature description - no "fixed X" framing, since no user was ever affected.
5. **Gunsmith mode is backend-only right now.** `backend/optimizer/gunsmith.py`, the `/build/gunsmith-tasks` and `/build/gunsmith-solve` endpoints, and `backend/data/gunsmith_tasks.json` are fully implemented and tested, but there is no frontend UI wired up to them. Do not describe it as a live/available feature in README.md, README_ZH.md, patch notes, or any other user-facing doc until the frontend exposes it.
6. **Code comments:** first-person/imperative developer voice ("track the hovered card so we can reset it"), never third-person ("this function handles..."). No emojis in code or comments unless explicitly asked.
7. **No em dash (—)** anywhere in written output - chat replies, commit messages, docs, code comments. Use a regular hyphen (`-`) instead. Even better, avoid hyphens altogether if possible.
8. **Chinese-language text** (README_ZH.md edits, GitHub replies, translations) uses fullwidth Chinese punctuation (`,` `。` `:` `;` `?` `!`), not halfwidth ASCII equivalents - except inside inline code/technical tokens.
9. **Release news ownership:** as specified in `CONTRIBUTING.md`, do not add or edit `frontend/news/` posts or `manifest.json` as part of a feature or fix PR. Morph1ne writes and publishes release notes, version bumps, and the news feed after changes ship.
10. **"The optimizer" means Explore mode.** Explore mode (`backend/optimizer/explore.py`, `POST /build/explore`, `frontend/modules/optimizer.js`) is the default and only supported optimizer mode - single-solve mode is scrapped and permanently disabled. Whenever a prompt refers to "the optimizer" without qualification, assume it means Explore mode specifically.

## Quick reference: don't run these directly

- `sync_tarkov_dev.py` - production-only manual resync tool; local dev gets data via `reset.py`/`launch.bat` automatically.
- Anything that starts a frontend dev server or opens a browser - the maintainer handles frontend verification.
